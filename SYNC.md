## How to use this file

1. **Starting a session:** read the last 2–3 entries below, then verify against reality with `git log --oneline -20` and `git status`. This file records intent and context; git is ground truth. If git shows commits or working-tree changes not mentioned in the log, that's undocumented work from the other engineer — inspect it before building on it or changing it.
2. **Ending a session, or before switching tools:** append a new entry at the top using the template below. Keep it short — bullet points, not prose. This is a standup log, not documentation; real documentation belongs in `docs/`.
3. **Open questions:** if you need an answer from "the other engineer" (human or AI) before proceeding, write it under `Open questions` in your entry. Whoever picks up next answers it in their own entry rather than editing yours.
4. If this file grows past ~15 entries, move the older ones to `docs/SYNC_ARCHIVE.md` and keep this file to the recent handful. Keep entries short: findings and measurements that will matter later belong in `docs/`, with the entry linking to them. Don't read the archive at session start; grep it only when you need the history behind something.

### What's actually landed (Stages 1-4, all on `realism-pass`, all pushed)

**Stage 1 — turned off leftover "retro console" rendering settings.** The game's rendering code still carried settings from an abandoned older art direction (a deliberate late-90s/early-2000s console look) that the project's own direction docs had already moved past in writing, but nobody had gone back and turned off in code. Concretely: flat per-facet shading was on everywhere (the single biggest "toy" signal), colours were being crushed to 32 steps per channel (visible banding), and UI/sign textures were pixel-filtered like retro game art. All three switched off. Added proper anti-aliasing (SMAA), which wasn't there before. Also fixed the project's own documentation, which had the story backwards: it blamed `ART_DIRECTION.md` for being stale when actually that file was already correct, and `docs/VISUAL_LANGUAGE.md` was the one still describing and configuring the old look.

**Stage 2 — the colour grade.** Three changes to how the final image is toned: (1) a "black lift" so shadows read as dark blue-grey instead of crushing to flat black — this does NOT make the game brighter or reduce the darkness-between-streetlights identity the game is known for, it only affects how dark the darkest pixels can get; (2) a subtle colour push — shadows lean slightly cool/teal, highlights lean slightly warm/amber, instead of a flat overall saturation boost; (3) tighter, more selective bloom around lights, so glow reads as coming from something genuinely bright rather than hazing over the whole image. Also added a live-tuning console tool, `zealot.grade.set({...})`, so these can be adjusted by eye without a rebuild — see action item 1 below, this is the one still waiting on Daniel's actual visual judgment.

**Stage 3 — texture standard and material realism settings.** Wrote down an actual standard for future textures (resolution, which maps, naming) into `docs/TECHNICAL.md`. Added the plumbing for normal maps and packed AO/roughness/metal textures to the game's procedural material system (no content uses it yet — it's there for when Stage 3c or later work needs it). Fixed Dreams' lit sign panel, which was far too matte (a roughness value of 0.82, essentially chalk) — now 0.45, so the tubes above it leave a visible soft sheen on the panel, which you can see in the screenshots. Glass materials now have their shininess capped low, ready to actually reflect once an environment map exists. **Explicitly did NOT do** one thing the original plan asked for: raising the "metalness" of things like railings, bollards and bins to near-chrome levels. On inspecting the actual code, every one of those already had sensible values matching a weathered, painted, oxidised look — the plan's instruction would have made painted council street furniture look like polished chrome, which is a regression against the grounded photographic look Daniel wants, not a fix. Struck it with the reasoning written down rather than doing it mechanically.

**Stage 4 — environment map, wet roads, and light-reflection streaks.** Three pieces:
1. *Environment map* — PBR materials (anything with "metalness") need something to reflect or they look flat regardless of their settings. The plan called for a Blender-rendered or licensed photo panorama; neither is available in this sandboxed session (no Blender, no way to responsibly license-track a downloaded image), so a different, legitimate technique was used instead: the game takes one photo of its own already-built world, once, right after loading, and uses that as the reflection source. This actually has a real advantage — the reflections tint with this specific location's actual colours (the cold Dreams tubes, the sodium streetlamp) rather than a generic stand-in sky. A real Blender render can swap in later with no other code changes needed.
2. *Wet ground* — a new procedurally-generated "puddle mask" texture decides where the road and pavement are wet versus dry, and that drives darker colour, lower roughness (shininess) and flatter reflections in those spots. First attempt at the noise pattern covered about half of every street in "wet" — caught by actually measuring the distribution rather than eyeballing it, and refit down to a realistic scattered-puddle look.
3. *Light streaks* — the classic "cheap trick that sells wet ground" in games: a stretched glowing streak lying flat on the road under each light, visible only where the puddle mask says there's water. Every streetlight in the game got one automatically (reusing data the game already had — no new authoring needed), plus one for Dreams' own tubes. You can see a clear example under the MCR1 shop sign in the Stage 4 screenshots.
Also explicitly did NOT retire an older, separate "broken reflection" decal system near several hero buildings, which the plan had said to remove — on inspection that system covers glow at *every* hero building citywide (not just Dreams) and does a different job (always-on, not wetness-dependent). Flagged for Daniel to look at both together rather than deleting authored content across the map without that comparison — action item 5 below (not one Daniel raised in his message just now, but still open from the Stage 4 entry).
